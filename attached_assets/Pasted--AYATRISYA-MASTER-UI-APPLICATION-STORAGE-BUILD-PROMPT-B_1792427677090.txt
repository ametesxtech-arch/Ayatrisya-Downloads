# AYATRISYA — MASTER UI, APPLICATION & STORAGE BUILD PROMPT
## By Ametesx | Premium AI Workspace | Production-Quality Frontend

Act as a principal frontend engineer, product designer, application architect, accessibility specialist, and storage engineer.

Build **Ayatrisya**, an original, premium AI workspace under the parent brand Ametesx. Create a complete, polished, responsive, functional application—not merely a landing page or static mockup.

The application UI and storage system will be developed in Replit. A separate engineering environment is developing Ayatrisya's own AI models. Therefore, design the application around clean model interfaces without substituting third-party AI APIs or pretending that unfinished models already work.

Do not stop after planning. Inspect the existing project, preserve working features, implement the application in logical phases, run available tests, fix errors, and report what is genuinely functional.

# 1. NON-NEGOTIABLE PROJECT RULES

1. Product name: **Ayatrisya**. Parent brand: **Ametesx**. Keep spelling consistent.
2. Do not redesign the product into a generic ChatGPT clone.
3. Do not integrate OpenAI, Gemini, Claude, Groq, OpenRouter, Hugging Face Inference API, or other third-party AI inference APIs.
4. Do not create fake AI responses and present them as real model output.
5. Do not claim Google Drive synchronization, authentication, file upload, or model inference works until it has been tested end to end.
6. Build functional local storage before implementing Google Drive synchronization.
7. Use modular components, typed interfaces, clean error handling, and reusable design tokens.
8. Never expose Firebase service-account credentials, private keys, OAuth client secrets, or tokens in frontend code.
9. Never store private user content in an Ayatrisya-owned database by default.
10. Do not hardcode fake usage statistics, fabricated model accuracy, fake files, or imaginary sync statuses.
11. Do not remove existing project functionality without inspecting its dependencies and explaining the reason.
12. Make the UI usable on desktop, tablet, and mobile.

# 10. LOCAL-FIRST STORAGE SYSTEM

This is a core product feature, not an afterthought.

## Browser storage

Use IndexedDB through a well-maintained library or a small, tested repository abstraction.

Persist:
- Conversations and messages.
- Conversation titles and timestamps.
- User interface preferences.
- Project metadata.
- User-created notes.
- Attachment metadata.
- Local references to files where browser permissions allow them.
- Sync queue and synchronization metadata.

Use object stores with versioned schema migrations.

Recommended conceptual stores:
- `profiles`
- `conversations`
- `messages`
- `projects`
- `projectItems`
- `attachments`
- `preferences`
- `syncQueue`
- `syncMetadata`

Avoid storing large base64 strings inside conversation records. Store binary blobs separately when appropriate and maintain references.

Requirements:
- IndexedDB transactions for related changes.
- Search and pagination for large histories.
- Data integrity checks.
- Safe deletion and cleanup.
- Export and restore.
- Graceful handling of storage failures.
- Schema migrations.
- A local storage repository interface that can be unit tested.

Do not promise a guaranteed 4 GB quota. Browser quotas vary by browser, device, available disk space, and storage policies. Use `navigator.storage.estimate()` when supported and report estimates accurately.

Request persistent browser storage when appropriate, but never claim the request guarantees unlimited or permanent storage.

## Local storage interface

Create a Storage Settings page showing:
- Storage mode.
- Approximate used storage when available.
- Approximate available quota when available.
- Local conversation count.
- Local project count.
- Drive connection status.
- Last successful sync, if known.
- Pending sync operations, if any.

## Backup and restore

- Export project metadata and user-owned content where technically permitted.

- Detect duplicate IDs.

# 11. GOOGLE DRIVE — OPTIONAL USER-OWNED SYNC

Google Drive integration is optional. The application must remain fully useful without it.

Implement Drive integration only after local storage is stable and tested.

## Authentication and permissions

- Use an appropriate Google OAuth flow.
- Request the narrowest viable scope.
- Prefer `drive.file` when compatible with the required application workflow.
- Do not request full Drive access without a demonstrated technical need and explicit approval.
- Do not place client secrets in frontend source code.
- Do not log OAuth tokens.
- Do not send files through an Ayatrisya-owned content database as an intermediate step.

If the required OAuth configuration cannot be completed in Replit, build the integration boundary, provide exact setup instructions, and clearly mark it as not yet connected. Do not simulate a successful connection.

## Drive folder

Offer a user-authorized Ayatrisya folder in the user's Google Drive.

Organize supported content into clear folders, for example:
- `Ayatrisya/Backups`
- `Ayatrisya/Projects`
- `Ayatrisya/Exports`

Create folders through the actual Drive API only after successful authorization. Store returned Drive file IDs; never guess them.

Do not upload all files automatically on first connection. Explain what will sync and obtain user consent.

## Synchronization

Implement a controlled sync engine:
- Upload new or modified eligible files.
- Download changes where the user has authorized bidirectional sync.
- Track remote file IDs and modification metadata.
- Maintain a pending operation queue.
- Retry transient failures safely.
- Detect conflicts.
- Avoid infinite upload/download loops.
- Prevent duplicate files where possible.
- Display progress and actionable error messages.
- Allow pause, resume, and manual sync.
- Show the last confirmed successful operation.
- Never label a queued or failed upload as completed.

Handle deleted files and conflict resolution explicitly. Do not silently overwrite a newer version.

Use stable identifiers, checksums where appropriate, and version metadata. Do not assume Drive metadata alone guarantees conflict-free synchronization.

## Cross-device behavior

Explain the distinction:
- Browser local storage is device/browser-specific.
- Google Drive provides cross-device access only for content that has actually synchronized successfully.
- Desktop files remain on the computer unless the user enables a supported sync or backup action.
- Drive permissions and offline availability depend on Google and the device.

Do not promise instant or perfect synchronization.
